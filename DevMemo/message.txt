# Forgot to reset skills — 포트폴리오 게임 개발 계획서

> **핵심 원칙: 빠르게 "완성도 있는 뼈대(Vertical Slice)"를 먼저 만든다.**
> 13개 시스템을 전부 구현하는 게 목표가 아니다. **1회차 루프가 처음부터 끝까지 매끄럽게 도는 작은 게임**을 먼저 완성하고, 그 위에 살을 붙인다.

---

## 0. 프로젝트 한눈에 보기

| 항목 | 결정 |
|---|---|
| 엔진 / 언어 | Unity / C# (현재 레포 그대로) |
| 시점 / 차원 | **2D 횡스크롤 액션** (레퍼런스: BlazBlue Entropy Effect) |
| 장르 | 로그라이크 핵앤슬래시 + 보스 |
| 개발 기간 | **3~4개월** |
| 개발자 | 개발 전공 / 타 업계 경력자, **Unity는 처음** |
| 현재 진행 | 좌우 이동 + 점프 구현 완료 (커밋 1개) |
| 1차 목표 | **버티컬 슬라이스 = 플레이 가능한 1회차 완전 루프** |

> 개발 자체는 익숙한 분이므로, 이 문서는 "C# 문법"이 아니라 **Unity에 특화된 설계 패턴과 우선순위 판단**에 집중한다. Unity에서 처음 개발자들이 가장 자주 무너지는 지점은 문법이 아니라 **씬/오브젝트 수명 관리, 데이터 영속성, 결합도**다.

## 1. 가장 먼저 정의해야 할 것 — "뼈대"의 정확한 정의

학생이 적은 기획은 풍부하지만, 그대로 가면 **어느 시스템도 완성되지 않은 채 4개월이 끝난다.** 포트폴리오에서 가장 안 좋은 결과는 "기능 30개가 다 50%인 게임"이다. 반대로 가장 좋은 결과는 **"기능 8개가 100%인, 끝까지 플레이되는 게임"**이다.

그래서 첫 목표를 이렇게 못박는다.

### 🎯 버티컬 슬라이스 (Definition of Done)

아래가 **하나의 빈틈 없는 루프**로 돌면, 그게 곧 게임의 뼈대다.

```
[마을/허브] → 스테이지 진입 → 적과 전투(핵앤슬래시) → 스테이지 클리어
   → 보상으로 스킬/아이템 획득 → 다음 스테이지 → ... → 보스
   → (사망 시) 회귀: 1스테이지로. 능력·업적은 유지, 아이템·레벨은 소실
   → 다시 마을 → 반복
```

이 루프가 돌기 위해 **반드시** 필요한 것만 추리면:

1. 플레이어 전투 — 근접 공격 + 액티브 스킬 1개 + 패시브 스킬 1개 + HP/MP
2. 적 2종 + 보스 1체
3. 스테이지 2~3개 + 스테이지 전환
4. 스테이지 클리어 판정 + 보상 지급
5. **회귀 시스템** — 죽으면 1스테이지로, 데이터 일부만 유지 (이게 로그라이크의 심장)
6. 마을(허브) 1개 — 휴식 / 스킬 장착
7. 저장 / 로드 (영구 데이터)
8. 최소 UI — HP/MP, 스킬 슬롯, 스테이지·회차 표시

**이 8개를 제외한 모든 것은 일단 보류한다.** 뼈대가 돌기 시작한 다음에 붙인다.

## 2. 시스템 우선순위 — 13개 기획을 3단계로 분류

학생이 제시한 시스템 전부를 **Must / Later / Defer**로 나눴다. 기획을 버리는 게 아니라 **순서를 정하는 것**이다.

### 🟢 Must — 뼈대(버티컬 슬라이스)에 반드시 포함

| 시스템 | 뼈대 버전에서의 범위 (의도적으로 축소) |
|---|---|
| **1. 회귀** | 죽으면 1스테이지. **영구 데이터(능력·업적·격)** vs **회차 데이터(레벨·아이템·장착)** 분리. 이 분리가 아키텍처의 핵심. |
| **8. 스킬** | 액티브 1 + 패시브 1 장착 구조. 마나 소모. 스킬은 **ScriptableObject**로 데이터화. 처음엔 3~5개면 충분. |
| **9. 스탯** | 체력/마나 + 공격력 정도. 복잡한 체근민·스탯 분배는 나중. |
| **10. 레벨** | 경험치 → 레벨업 → 스탯 소폭 상승. 회귀 시 소실. |
| **11. 적** | 2종 + 보스 1. "격이 안 맞으면 못 이김"은 **나중**. 지금은 그냥 정상 전투. |
| **13. 게임플레이** | 핵앤슬래시 + 보스 + 스테이지 후 마을 휴식. |

### 🟡 Later — 뼈대 완성 후 (3~4개월 안에 여유 되면)

| 시스템 | 메모 |
|---|---|
| **2. 퀘스트** | 뼈대에선 "목표 1개 + 보상 1개"의 **최소 퀘스트 트래커**만. 메인/서브/특수 분기와 중복은 Later. |
| **3. 특수 능력 (정보 확인 창)** | "적/아이템/NPC 정보 표시 창"은 비교적 싸고 **포트폴리오에서 눈에 띄는 차별점**. 뼈대 후 1순위 추가. |
| **6. NPC** | "계약 → 스킬 사용" 1개만 먼저. 관계도/호감도/분기 적아 전환은 Later. |
| **7. 업적** | "업적 → 격(格) 상승 → 추가 강함"의 **최소 격 시스템**. 메타 진행의 차별점이라 가치 높음. |
| **12. 무기/아이템** | 회차 내 도움 주는 소모성/장비 아이템 몇 종. 적·NPC 상호작용은 Later. |
| **4. 스테이지 (히든/스킵)** | 히든 던전, 초반 스킵은 콘텐츠가 쌓인 뒤. |

### 🔴 Defer — 포트폴리오 범위 밖 (스코프 관리상 명시적으로 제외)

> 이건 "안 한다"가 아니라 **"이 포트폴리오에선 안 한다"**는 선긋기다. 적어두면 나중에 욕심에 휩쓸리지 않는다.

- **5. 난이도 자동 밸런싱** (조건 만족 시 난이도 증감, 초반 후반용 스킬 패널티) — 콘텐츠가 많아야 의미 있음. 정적 난이도로 시작.
- **3. 보류 항목들** — 빙의(다른 NPC 시점), 제4의 벽(정신공격 면역).
- **4. 게임 속 특수 스테이지** (fps / aos / 카드 미니게임) — 각각이 별도 게임. 절대 손대지 말 것.
- **6. NPC 관계도 그래프 / 호감도 / 관측 시스템** — 시스템 자체는 멋지지만 비용 대비 화면에 잘 안 보임.
- **2. 퀘스트 중복 / 동적 생성 / 강제성 패널티** — 콘텐츠 양이 받쳐줘야 함.

> **판단 기준:** "이 기능이 화면에서 눈에 보이고, 플레이어가 만지는가?"를 기준으로 Defer를 정했다. 관계도 그래프처럼 내부 로직만 복잡하고 화면 체감이 적은 건 포트폴리오 가성비가 낮다.

## 3. 아키텍처 설계 — 처음에 이걸 잡으면 나중에 안 무너진다

Unity가 처음인 경력 개발자에게 가장 중요한 절(節). **뼈대 속도는 결국 초기 구조가 결정한다.** 여기서 며칠 더 쓰는 게 나중에 몇 주를 아낀다.

### 3.1 데이터 영속성 — 회귀 시스템의 정체

학생 기획의 회귀 규칙을 그대로 코드 구조로 번역하면 아래가 된다. **이게 이 게임 아키텍처의 척추다.**

> 아이템은 잃음 / 특수능력은 안 잃음 / 레벨은 잃음 / 업적은 안 잃음

이건 곧 **"두 종류의 데이터를 물리적으로 분리하라"**는 뜻이다.

```csharp
// 영구 데이터 — 죽어도 유지, 디스크에 저장
[Serializable]
public class PlayerProgress
{
    public List<string> unlockedAbilityIds;   // 특수 능력 (안 잃음)
    public List<string> achievementIds;        // 업적 (안 잃음)
    public int rank;                           // 격(格) — 메타 진행
    public List<string> unlockedSkillPool;     // 한번 해금한 스킬 풀
}

// 회차 데이터 — 죽으면 폐기하고 새로 생성
[Serializable]
public class RunState
{
    public int currentStage = 1;
    public int level = 1;
    public int exp = 0;
    public int hp, mp;
    public List<string> inventory;             // 아이템 (잃음)
    public string equippedActiveSkillId;
    public string equippedPassiveSkillId;
    public List<QuestProgress> activeQuests;
}
```

**사망 처리는 이렇게 한 줄로 끝나야 정상이다:**

```csharp
void OnPlayerDeath()
{
    SaveSystem.Save(playerProgress);   // 영구 데이터만 디스크에 보존
    runState = new RunState();          // 회차 데이터는 통째로 폐기 → 1스테이지
    LoadStage(1);
}
```

> ⚠️ **가장 흔한 실수:** 플레이어 스탯·인벤토리·업적을 한 MonoBehaviour에 다 때려넣는 것. 그러면 "죽었을 때 뭘 남기고 뭘 지울지"가 if문 지옥이 된다. **처음부터 `PlayerProgress`(영구) / `RunState`(회차)를 두 클래스로 쪼개면 회귀가 거의 공짜로 구현된다.** 이 분리 하나가 이 게임 설계의 80%다.

### 3.2 데이터 주도 설계 — ScriptableObject

스킬·적·아이템·스탯을 **코드가 아니라 데이터(에셋)로** 만든다. Unity의 `ScriptableObject`가 이걸 위한 도구다.

```csharp
[CreateAssetMenu(menuName = "Game/Skill")]
public class SkillData : ScriptableObject
{
    public string id;
    public string displayName;
    public SkillType type;        // Active / Passive
    public int manaCost;
    public float cooldown;
    public float damage;
    public GameObject vfxPrefab;
    // 발동 로직은 별도 전략 클래스/그래프로 분리
}
```

**왜 이렇게 하는가 (Why):**
- 새 스킬 추가 = 코드 수정 없이 **에셋 하나 복제 후 값만 바꾸기**. 콘텐츠 양치기가 핵심인 로그라이크에서 압도적으로 빠르다.
- 밸런스 수정(데미지·마나)을 **인스펙터에서 즉시** 조정. 빌드 불필요.
- 적(`EnemyData`), 아이템(`ItemData`)도 동일 패턴 → 콘텐츠 채우는 단계(Phase 5)가 폭발적으로 빨라진다.

> 적용 대상: 스킬, 적, 아이템, 업적, (나중에) 퀘스트. 이 다섯은 무조건 ScriptableObject로.

### 3.3 결합도 — 이벤트로 풀어라

Unity 초심자가 `GameObject.Find()`, `GetComponent()`를 남발하면 곧 **모든 게 모든 걸 직접 참조하는 스파게티**가 된다. 시스템이 13개나 되는 이 게임에선 치명적이다.

- **UI ↔ 게임 로직**은 직접 참조하지 말고 **이벤트**로 연결한다. (예: `HP 변경` 이벤트 → UI가 구독해서 갱신)
- 권장: **C# `event` / `Action`** 또는 **ScriptableObject 이벤트 채널**. (DI 프레임워크 VContainer/Zenject는 이번 스코프엔 과함. 도입하지 말 것.)
- 예: 적 사망 → `OnEnemyKilled` 이벤트 발행 → 경험치 시스템, 퀘스트 시스템, 업적 시스템이 **각자 구독**. 적은 누가 듣는지 몰라도 됨 → 시스템을 독립적으로 추가/제거 가능.

> **이게 왜 뼈대 속도에 직결되나:** 나중에 "퀘스트", "업적"을 붙일 때 기존 전투 코드를 건드리지 않고 **이벤트만 구독**하면 끝나기 때문이다. 결합도를 낮춰두면 Later 시스템 추가가 며칠 → 몇 시간이 된다.

### 3.4 플레이어 / 적 — 상태 머신(FSM)

이동·점프가 늘어나 공격·피격·대시·사망까지 가면 `bool` 플래그가 엉킨다. **간단한 FSM**으로 상태(Idle/Move/Jump/Attack/Hurt/Dead)를 명시적으로 관리한다. 적도 동일 패턴(Idle/Chase/Attack/Hurt/Dead). 거창한 라이브러리 필요 없음 — `enum` + `switch` 수준이면 충분하다.

### 3.5 오브젝트 풀링 & 씬 구조 (가볍게)

- **풀링:** 적·투사체·이펙트는 생성/파괴 반복이 잦다 → `UnityEngine.Pool.ObjectPool<T>`(2021+ 내장)로 풀링. GC 스파이크 예방. 단, **뼈대 단계에서 과하게 미리 최적화하지 말 것** — 적이 화면에 많아지는 시점(Phase 5)에 적용해도 늦지 않다.
- **씬 구조:** 마을·스테이지를 씬으로 분리하고 **Additive Loading**으로 UI 씬은 항상 위에 유지. 또는 스테이지를 프리팹으로 두고 한 씬에서 교체하는 방식도 초기엔 더 간단하다.

### 3.6 권장 초기 세팅 (Phase 0에서 한 번에)

- **렌더 파이프라인:** URP + **2D Renderer**. (2D 라이팅·셰이더 그래프 활용 용이. Built-in 쓰지 말 것.)
- **입력:** 새 **Input System** 패키지. 키 리바인딩·게임패드 대응이 쉬움. 기획의 "입력키 복잡하지 않게"와도 맞음.
- **폴더 구조 + Assembly Definition(.asmdef):** 시스템별로 어셈블리를 쪼개 두면 컴파일 시간이 줄고 의존 방향이 강제된다. (`Core`, `Player`, `Enemy`, `Skill`, `UI`, `Save` 등)
- **버전 관리:** Git + **Git LFS**(스프라이트·오디오 등 바이너리용). `.gitignore`에 `Library/`, `Temp/` 반드시 포함. (현재 커밋에 이게 제대로 됐는지 점검 필요.)

## 4. 단계별 로드맵 (3~4개월 / 약 14주)

> 주(週) 수는 풀타임 기준 가늠치다. 병행이면 늘려 잡되 **순서는 유지**한다. 각 Phase 끝에는 반드시 **"돌아가는 빌드"**가 나와야 한다 — 절대 한 번에 다 만들고 합치지 않는다.

### Phase 0 — 토대 (약 1주)
URP 2D·Input System 세팅, 폴더/asmdef 구조, Git LFS 점검, `GameManager`·`SaveSystem` 골격, 데이터 클래스 2개(`PlayerProgress`/`RunState`) 정의.
- ✅ **완료 기준:** 빈 씬에서 플레이어가 이동·점프(기존 코드 이식), 저장/로드 버튼이 더미 데이터로 동작.

### Phase 1 — 코어 전투 (약 2~3주)
근접 공격, 데미지/피격 시스템(`IDamageable` 인터페이스), HP/MP, 적 1종(추격+공격), 히트스톱·넉백 등 기본 타격감, 플레이어/적 FSM.
- ✅ **완료 기준:** 적과 싸워서 죽이고, 맞으면 죽는다. "때리는 맛"이 어느 정도 난다.

### Phase 2 — 데이터 아키텍처 & 회귀 (약 2주)
`SkillData`/`EnemyData` ScriptableObject화, 경험치·레벨업, **회귀 루프 완성**(사망 → RunState 폐기 → 1스테이지, PlayerProgress 유지), 디스크 저장/로드.
- ✅ **완료 기준:** 죽으면 레벨·아이템은 사라지고, (테스트용) 영구 능력·업적은 유지된 채 1스테이지로 돌아간다. **로그라이크의 심장이 뛴다.**

### Phase 3 — 스테이지 & 루프 닫기 (약 2~3주)
스테이지 전환, 스테이지 클리어 판정, 마을(허브) 씬, 마을↔스테이지 이동, 회차/스테이지 표시 UI.
- ✅ **완료 기준:** 마을 → 스테이지 1 → 클리어 → 스테이지 2 → ... → 죽음 → 마을, 이 **루프가 끊김 없이 돈다.** ← **이 시점이 "뼈대 완성"이다.**

### Phase 4 — 스킬 & 보상 (약 2주)
액티브/패시브 1개씩 장착 UI, 스킬 발동·마나 소모·쿨다운, **스테이지 클리어 보상으로 스킬/아이템 지급**, 스킬 획득 알림.
- ✅ **완료 기준:** 클리어할수록 강해지는 **성장 보상 루프**가 닫힌다.

### Phase 5 — 보스 & 콘텐츠 채우기 (약 2주)
보스 1체(패턴 2~3개), 적 2~3종 추가, 스테이지 2~3개 분량 콘텐츠, (여유 시) **정보 확인 창** 또는 **최소 격(格) 시스템** 중 하나.
- ✅ **완료 기준:** 처음부터 보스까지 한 판이 그럴듯하게 채워진다.

### Phase 6 — 폴리시 & 포트폴리오화 (약 2주)
게임 필(화면 흔들림·파티클·사운드), UI 정리, 타이틀/일시정지, 빌드(WebGL 또는 PC), **README + 아키텍처 다이어그램 + 플레이 영상/GIF**.
- ✅ **완료 기준:** 남에게 보여줄 수 있는 빌드와 깃허브 문서가 완성된다.

> **버퍼:** 위 합계가 약 13~14주다. 3~4개월이면 **Phase 5의 Later 항목(정보 창/격 시스템)** 정도까지 현실적으로 도달 가능. 그 이상(퀘스트 분기, NPC 관계도)은 무리하지 말 것.

## 5. 포트폴리오 관점 — 평가자는 무엇을 보는가

이건 학생이 놓치기 쉬운 부분이라 따로 짚는다. 채용/평가 시점에서 강하게 어필되는 순서는:

1. **끝까지 플레이되는가** — 미완성 데모보다 짧아도 완결된 루프가 압도적으로 강하다.
2. **코드 구조** — `PlayerProgress`/`RunState` 분리, ScriptableObject 데이터 설계, 이벤트 기반 결합도 관리는 **그 자체가 실력 증명**이다. README에 아키텍처 다이어그램으로 보여줄 것.
3. **하나의 차별점** — 이 게임에선 **회귀 + 격(格) 메타 진행** 또는 **정보 확인 창**이 후보. 욕심내지 말고 **딱 하나만** 완성도 있게.
4. **게임 필** — 타격감·이펙트·사운드. Phase 6에서 짧게라도 반드시.

> 즉, 학생의 방대한 기획서는 **"비전 문서"로 README에 첨부**하고, 실제 빌드는 그중 완성된 부분만 보여주는 전략이 가장 강하다. "이런 큰 그림을 설계했고, 그중 핵심 루프를 이만큼 구현했다"가 좋은 서사다.
